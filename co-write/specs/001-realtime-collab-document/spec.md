# Feature Specification: 실시간 협업 문서 편집 및 관리 시스템

**Feature Branch**: `001-realtime-collab-document`

**Created**: 2026-06-14

**Status**: Draft

**Input**: core/edit-document(실시간 편집) 및 core/user-and-document(CRUD 관리) 모듈 명세

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 실시간 동시 편집 (Priority: P1)

여러 사용자가 동시에 같은 문서를 열고 편집할 때, 각자의 편집 내용이 충돌 없이 모든 참여자 화면에
실시간으로 반영된다. 사용자 A가 문서 앞부분을 수정하는 동안 사용자 B가 뒷부분을 수정해도
두 변경 내용이 모두 올바르게 병합되어 표시된다.

**Why this priority**: 협업 편집 시스템의 핵심 가치이며, 이 기능 없이는 서비스 자체가 성립하지 않는다.

**Independent Test**: 두 개의 별도 클라이언트를 동일 문서에 연결하고 동시에 편집 요청을 보낸 뒤,
양쪽 클라이언트에서 동일한 최종 문서 내용을 확인함으로써 독립 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 두 사용자가 동일 문서에 연결된 상태에서, **When** 두 사용자가 서로 다른 위치에 텍스트를 동시에 삽입하면, **Then** 양쪽 모두 두 삽입 내용이 모두 반영된 동일한 문서를 확인할 수 있다.
2. **Given** 두 사용자가 동일 위치에 동시에 텍스트를 삽입하면, **When** 서버가 OT 알고리즘으로 충돌을 해결하면, **Then** 두 사용자 모두 결정론적으로 동일한 순서로 병합된 결과를 확인한다.
3. **Given** 사용자가 편집 중에 네트워크가 일시 끊겼다 재연결되면, **When** 마지막 알려진 버전 이후 변경 내용을 요청하면, **Then** 누락된 편집 내용이 정상 복구된다.

---

### User Story 2 - 편집 내용 자동 저장 (Priority: P2)

사용자가 문서를 편집할 때 시스템이 편집 횟수를 추적하여, 10번의 편집이 누적되면 자동으로
현재 문서 상태를 영구 저장소에 저장한다. 사용자는 별도의 저장 버튼을 누르지 않아도 된다.

**Why this priority**: 데이터 유실 방지를 위한 핵심 기능이다. 실시간 편집 기능과 함께 동작해야 하지만
별도로 검증 가능하다.

**Independent Test**: 단일 문서에 10번의 편집 요청을 순차적으로 보낸 뒤, 영구 저장소에 최신 문서
내용이 저장되었는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 문서에 9번의 편집이 발생한 상태에서, **When** 10번째 편집이 발생하면, **Then** 시스템이 자동으로 현재 문서 내용을 DB에 저장한다.
2. **Given** 자동 저장이 완료된 후, **When** 추가 편집이 계속되면, **Then** 카운터가 리셋되어 다음 10번 편집 후 다시 저장된다.
3. **Given** 편집 중 오류가 발생하면, **When** 저장에 실패하더라도, **Then** 오류가 로그에 기록되고 다음 편집 요청은 정상 처리된다.

---

### User Story 3 - 문서 생성 및 관리 (Priority: P3)

사용자는 새 문서를 생성하고, 기존 문서 목록을 조회하고, 문서 정보를 수정하거나 삭제할 수 있다.
문서에 다른 사용자를 참여자로 초대하거나 제거할 수도 있다.

**Why this priority**: 실시간 편집의 전제 조건이지만, CRUD 기능 자체는 편집 기능과 독립적으로
검증 가능하다.

**Independent Test**: 문서를 생성하고, 조회하고, 내용을 수정하고, 삭제하는 흐름을 순서대로 실행하여
각 단계의 결과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인된 사용자가, **When** 새 문서 생성을 요청하면, **Then** 문서가 생성되고 사용자가 소유자로 등록된다.
2. **Given** 문서 소유자가, **When** 다른 사용자를 참여자로 추가하면, **Then** 해당 사용자가 문서를 편집할 수 있게 된다.
3. **Given** 문서 소유자가, **When** 문서 삭제를 요청하면, **Then** 문서와 관련 데이터가 삭제된다.

---

### User Story 4 - 사용자 인증 및 계정 관리 (Priority: P4)

사용자는 이메일/비밀번호 또는 Google 소셜 로그인으로 계정을 생성하고 로그인할 수 있다.
아이디·비밀번호 찾기 기능도 제공된다.

**Why this priority**: 모든 기능의 전제이지만, 인증 기능 자체는 이미 구현된 상태이며 유지/관리 관점에서 명세한다.

**Independent Test**: 신규 사용자 등록 → 로그인 → 인증 토큰 발급 → 보호된 API 호출 성공의 흐름으로
독립 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 미등록 사용자가, **When** 이메일과 비밀번호로 회원가입하면, **Then** 계정이 생성되고 로그인 가능한 상태가 된다.
2. **Given** 등록된 사용자가, **When** Google 계정으로 로그인하면, **Then** 계정이 연동되고 인증 토큰이 발급된다.
3. **Given** 사용자가 비밀번호를 잊었을 때, **When** 아이디 찾기 또는 비밀번호 재설정을 요청하면, **Then** 등록된 이메일로 안내가 전송된다.

---

### Edge Cases

- 두 사용자가 정확히 동일한 위치에 동시에 삽입할 때 순서 결정이 결정론적이어야 한다.
- 클라이언트의 버전이 서버가 보유한 가장 오래된 편집 이력보다 오래된 경우 전체 문서를 재전송해야 한다.
- 편집 요청의 `baseVersion`이 서버의 현재 버전보다 클 경우 즉시 거부해야 한다.
- 동시에 DB 저장 트리거가 여러 번 발생할 경우 분산 락으로 중복 저장을 방지해야 한다.
- 사용자가 문서 편집 중 로그아웃하면 WebSocket 연결이 정리되어야 한다.
- 메시지 브로커(Kafka)가 일시적으로 장애 상태일 때 편집 요청은 즉시 실패 처리되며, 사용자에게 서비스 복구 대기 안내가 전송된다. 요청은 서버 메모리에 보관하지 않는다.
- 문서 삭제 시 해당 문서를 편집 중인 참여자가 있다면, 전원에게 삭제 알림을 전송한 뒤 WebSocket 연결을 종료한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 동시에 수신된 여러 편집 연산을 OT 알고리즘으로 변환하여 충돌 없이 처리해야 한다.
- **FR-002**: 시스템은 편집 결과를 해당 문서에 연결된 모든 참여자에게 실시간으로 전달해야 한다.
- **FR-003**: 시스템은 편집 횟수가 10회에 도달할 때마다 문서를 영구 저장소에 자동 저장해야 한다.
- **FR-004**: 시스템은 편집 처리 실패 시 오류 원인을 로그로 기록하고, 실패한 편집 요청을 보낸 사용자에게 실패 알림과 재시도 안내를 전송하며, 다른 편집 요청 처리를 계속해야 한다.
- **FR-005**: 시스템은 모든 계층 간 데이터 전달에 DTO를 사용해야 하며, 엔티티를 직접 노출하지 않는다.
- **FR-006**: 각 클래스는 단일 책임만 가져야 하며, 하나의 클래스가 여러 도메인 역할을 동시에 수행하지 않는다.
- **FR-007**: 시스템은 문서의 생성, 단건 조회, 목록 조회, 수정, 삭제 기능을 API로 제공해야 한다. 삭제 시 해당 문서를 편집 중인 모든 참여자에게 삭제 알림을 전송하고 WebSocket 연결을 종료해야 한다.
- **FR-008**: 시스템은 사용자의 생성, 조회, 수정, 삭제 기능을 API로 제공해야 한다.
- **FR-009**: 시스템은 이메일/비밀번호 로그인 및 Google OAuth2 로그인을 지원해야 한다.
- **FR-010**: 시스템은 분산 환경에서 문서 저장 시 동시성 충돌을 방지하는 분산 락을 사용해야 한다.
- **FR-011**: 시스템은 편집 요청의 버전 유효성을 검증하여 잘못된 버전의 요청을 거부해야 한다.
- **FR-012**: 시스템은 사용자당 초당 최대 10회의 편집 요청만 허용하며, 초과 요청은 거부하고 해당 사용자에게 알림을 전송해야 한다.

### Key Entities

- **Document**: 협업 편집 문서. 고유 식별자, 제목, 내용, 현재 버전 번호, 소유자, 참여자 목록을 가진다.
- **User**: 시스템 사용자. 고유 식별자, 이메일, 비밀번호(해시), 로그인 방식(로컬/Google), 역할을 가진다.
- **Operation**: 편집 연산. 삽입(Insert) 또는 삭제(Delete) 유형이며, 대상 위치, 내용/개수, 세션 식별자, 연산 식별자, 기준 버전을 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 편집 내용이 전송된 후 1초 이내에 같은 문서의 모든 참여자 화면에 반영된다(동시 편집자 최대 10명 기준).
- **SC-002**: 동시에 편집 중인 모든 참여자의 최종 문서 내용이 100% 동일해야 한다(OT 수렴 보장).
- **SC-003**: 10번의 편집 발생 후 문서 내용이 영구 저장소에 정확하게 저장된다.
- **SC-004**: 편집 실패 발생 시 100%의 케이스에서 오류 로그가 기록되어야 한다.
- **SC-005**: 사용자는 로그인 후 3번 이내의 화면 전환으로 문서 편집을 시작할 수 있어야 한다.
- **SC-006**: 시스템은 동일 문서에 대한 동시 저장 요청 시 데이터 중복 또는 손실 없이 처리해야 한다.

## Clarifications

### Session 2026-06-14

- Q: 문서당 최대 동시 편집자 수는? → A: 10명 이하
- Q: 편집 실패 시 클라이언트 알림 방식은? → A: 실패한 사용자에게만 에러 메시지 및 재시도 안내 전송
- Q: 메시지 브로커 장애 시 동작은? → A: 즉시 실패 처리 후 서버 로그 기록, 사용자에게 복구 대기 안내 전송
- Q: 문서 삭제 시 편집 중인 참여자 처리는? → A: 모든 참여자에게 삭제 알림 전송 후 WebSocket 연결 종료
- Q: 편집 요청 속도 제한은? → A: 사용자당 초당 10회 이하, 초과 시 요청 거부 및 클라이언트 알림

## Assumptions

- 하나의 문서에 동시에 편집할 수 있는 최대 참여자 수는 10명이다.
- 사용자는 WebSocket을 지원하는 브라우저 환경에서 서비스를 이용한다.
- 편집 이력은 최근 200개까지 빠른 접근이 가능하며, 그 이전 이력이 필요한 경우 전체 문서 스냅샷으로 대체한다.
- 인증 토큰(JWT) 방식은 이미 구현되어 있으며, WebSocket 연결 시에도 동일한 토큰으로 인증한다.
- 문서 참여자 권한 관리(읽기 전용 vs 편집 가능)는 이번 스펙 범위에 포함되지 않는다.
- 모바일 앱 지원은 이번 스펙 범위에 포함되지 않으며, 브라우저 클라이언트만 대상으로 한다.
- 메시지 브로커를 통한 이벤트 발행은 Outbox 패턴으로 원자성이 보장된다.
